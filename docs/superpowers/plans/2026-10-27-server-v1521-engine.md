# v1.5.21浏览器引擎最小迁移计划

参考只读冻结的v1.5.21源码；保留a073执行桥接与001审计接纳、strictReadOnly完整存储取证、稳定任务身份、100组批/冷却、预占和未知不重放。不改原D:/doubao_1工作区、版本/安装器、全局网络、其他工作台。

1. 只移植orchestrator的saveDrafts/submitDrafts与必要依赖、driver的独立导入焦点/上传接口、native-drafts的完整正文/附件保存及逐条原消息回执。新导入独立页，成功单条持久入队后关闭；回执依赖唯一userMessageId，不等待视频生成。
2. 发送阶段始终仅完成投递。正常生产的生成确认单独在当前track租约内同步执行、先存确认意图再动作；后台仅只读取回，不继承已经归还或失效的租约，不自行确认。租约失效或未知意图不得重发。
3. 本次验收批次增加管理员显式、可审计、在封批前冻结的sendOnly标识；不改原001正文/ID。仅该批次导入/发送/track/重启均不触发生成确认或唤醒生成队列，普通批次保留租约保护的生成确认与结果回传。不得全局关闭autoConfirm或增加页面上限。
4. 在候选验证附件完整/失败保留、独立页生命周期、3条以上有限页面逐条接收、原userMessageId持久回执、sendOnly重启/track不确认、正常track确认需要有效租约、回报归还或拒绝后无后台输入。复用源124项已有通过证据，不将源测试当候选通过或本轮真实附件验收。
5. 先完成原001的恢复发布和接纳。随后新最小候选独立审查、PR/CI、限定豆包发布；只有sendOnly实际验证后，才交由既有验收聊天继续其余99条和100条原草稿回执核验。真实视频生成不在本次授权内。


实施细化：批次sendOnly只由管理员在单条已保存、尚未封批且无活动操作时显式启用，不能把验收任务改回生产生成；claim的import/send/track在payload携带同一冻结模式。原001快照、模板及nativePrompt不改；执行端使用草稿外层/本地任务元数据保存studioSendOnly，发送前持久化后才点击。发送回执持久保存userMessageId。

正常发送也先以投递模式完成原生队列，生成确认由track租约内的单次同步方法完成，确认页finally关闭；只有确认已发送或已观察生成才启动已有只读取回队列。后台runTask不继承输入租约。导入和确认的异步步骤增加仅服务器启用的租约检查取消，过期关闭本条专用页，迟到上传或确认回调不能继续操作。源代码版本的整页/附件校验保留，同时保留本服务的严格只读编号/账号范围核对及过渡正文等待。

用户补充：本次普通账号没有生成确认，只会提示额度不足，仅验收导入与发送回执。投递不等确认或生成，额度不足不等于未发送；沿用v1.5.21接受草稿的quota/sentAt保护，不清发送意图，不自动重发。正常任务先读明确失败/生成信号，再只在确有候选且当前租约有效时可选确认。迁移了这些直接相关的状态/恢复函数，未整文件覆盖服务器专属逻辑。
